5.1 DOCKER VIRTUALIZATION ENGINE & OCI CONTAINER SUBSYSTEM

1. THEORETICAL FOUNDATION OF CONTAINERIZED VGPU SLICING:
Traditional GPU virtualization (such as VMware ESXi vSphere with NVIDIA vGPU or 
dedicated PCI passthrough) operates at the hardware hypervisor boundary. A hypervisor 
must boot an entire independent guest operating system kernel, initialize virtual 
PCIe bridges, negotiate IOMMU page tables, and load full device driver binaries. 
This virtualization model carries heavy architectural penalties: each virtual 
instance consumes between 4 GB to 8 GB of host system RAM purely for guest OS 
overhead, and spinning up a new virtual accelerator instance requires between 45 to 
90 seconds of cold booting latency.

To eliminate this structural overhead, V-GPU replaces the heavy hypervisor layer 
with a container-native Open Container Initiative (OCI) execution runtime powered 
by Docker. In Linux operating system architecture, containers do not virtualize the 
underlying hardware; instead, they share the host operating system kernel while 
providing complete process, filesystem, and user isolation through native kernel 
primitives:
- Process ID (PID) Namespaces: Isolate process tree hierarchies so that workloads 
  running inside a virtual slice cannot observe, signal, or trace processes running 
  on the host or within neighboring tenant containers.
- Mount (MNT) Namespaces: Provide isolated root filesystem layers via overlayfs, 
  ensuring that user scripts cannot access host system binaries, configuration files, 
  or adjacent user datasets.
- Network (NET) Namespaces: Virtualize network routing tables, firewall filtering 
  rules, and IP socket tables, placing each virtual slice behind an isolated internal 
  virtual ethernet bridge.
- Control Groups (cgroups v2): Enforce hard limits and hierarchical accounting on 
  hardware resource consumption, specifically memory bytes and CPU compute shares.

2. WORKER IMAGE COMPOSITION (`vGPU-Worker.Dockerfile`):
The execution environment inside each virtual slice is standardized via a custom, 
minimal container image titled `vgpu-worker`. The image is derived from an official 
Debian-based `python:3.10-slim` distribution. All non-essential desktop packages, 
X11 servers, audio drivers, and documentation caches are purged to minimize attack 
surfaces and keep the compressed storage footprint below 280 megabytes. 

The image packages the exact scientific computing runtime required for modern AI/ML:
- BLAS/LAPACK Linear Algebra Accelerators: Pre-compiled OpenBLAS binaries linked 
  against NumPy and SciPy to maximize vector instruction throughput on host CPUs.
- Machine Learning Frameworks: Scikit-learn, lightweight PyTorch runtime modules, 
  and automated hyperparameter search utilities.
- Dynamic Execution Scaffolding: POSIX shell scripts that handle input script mounting, 
  argument injection, environment variable binding, and standardized metric logging.

5.1 DOCKER ENGINE INTERFACING & CONTAINER LIFECYCLE MANAGEMENT

1. THEORETICAL CONTROL PLANE BINDING:
The V-GPU control plane communicates with the container runtime through the official 
Docker Engine REST API via a local UNIX domain socket located at `/var/run/docker.sock` 
(or the named pipe `//./pipe/docker_engine` on Windows hosts). When a user or 
administrator initiates a slice creation command, the control plane does not invoke 
slow shell subprocess commands (`docker run`); instead, it issues asynchronous, 
non-blocking socket transactions via the Python Docker SDK.

2. RESOURCE CLAMPING & SWAP SUPPRESSION MECHANISM:
A critical flaw in standard multi-tenant Docker deployments is swap leakage. When a 
container exhausts its allocated RAM, the default Linux kernel memory manager does 
not terminate the process; instead, it pages out active memory pages to the host disk 
swap partition. In machine learning workloads, this causes catastrophic performance 
degradation known as "memory thrashing," where matrix multiplication stalls completely 
as tensors are repeatedly swapped across high-latency disk buses.

To enforce hard physical boundaries, V-GPU configures cgroup memory and swap limits 
identically:
$$\text{Memory Limit} = M_{\text{quota}}\text{ MB}, \quad \text{Memory+Swap Limit} = M_{\text{quota}}\text{ MB}$$
Because the swap allowance is clamped to zero additional bytes, any process that 
attempts to allocate memory beyond its provisioned vGPU quota is immediately trapped 
by the kernel's Out-Of-Memory (OOM) killer, protecting adjacent tenant slices.

3. CONTAINER LIFECYCLE CONTROLLER IMPLEMENTATION:

```python
import docker
from docker.errors import DockerException

class DockerRuntimeController:
    """
    Manages low-level OCI container instantiation and cgroup limit enforcement
    via the host Docker daemon socket.
    """
    def __init__(self):
        try:
            self.client = docker.from_env()
            self.client.ping()
            self.is_active = True
        except DockerException:
            # Fallback to high-fidelity mathematical emulation if daemon is absent
            self.client = None
            self.is_active = False

    def instantiate_slice_container(self, instance_id: str, memory_mb: int, compute_pct: int) -> str:
        if not self.is_active:
            return f"simulated-cgroup-{instance_id}"
            
        mem_str = f"{memory_mb}m"
        # 100,000 microseconds CFS scheduling period
        cfs_period = 100000
        cfs_quota = int(cfs_period * (compute_pct / 100.0))
        
        container = self.client.containers.run(
            image="vgpu-worker:latest",
            name=f"vgpu-{instance_id}",
            detach=True,
            mem_limit=mem_str,
            memswap_limit=mem_str,       # Hard clamp: zero swap allowance
            cpu_period=cfs_period,
            cpu_quota=cfs_quota,         # Fractional compute timeshare
            network_mode="bridge",
            environment={
                "VGPU_INSTANCE_ID": instance_id,
                "VGPU_VRAM_QUOTA_MB": str(memory_mb),
                "VGPU_COMPUTE_SHARE": str(compute_pct)
            }
        )
        return container.id
```

5.2 VIRTUAL GPU DRIVER & MEMORY SLICING (`core/vgpu_driver.py`)

1. THEORETICAL DRIVER ARCHITECTURE:
In bare-metal operating systems, physical GPU drivers (such as `nvidia.ko`) represent 
hardware as monolithic device character nodes located within `/dev/` (e.g., `/dev/nvidia0`, 
`/dev/nvidiactl`). Traditional device drivers possess no native awareness of multi-user 
quotas; any user process that opens the character device can issue unbounded memory 
allocation requests (`cudaMalloc`) until the physical onboard VRAM is completely 
exhausted.

The V-GPU driver (`core/vgpu_driver.py`) introduces a software-defined mediation layer 
that sits between incoming client requests and the physical hardware. It decouples 
physical accelerator state into two distinct domain models:
- Physical Device Entity (`VGPUDevice`): Tracks total onboard memory capacity, 
  cumulative unreserved memory margins, hardware core counts, PCIe bus identifiers, 
  operating frequencies, and junction temperatures.
- Virtual Slice Entity (`VGPUInstance`): Represents a software-bounded fraction of the 
  parent device. It maintains a distinct identity, an assigned container binding, 
  an isolated memory quota (in megabytes), and an active operational state (`IDLE`, 
  `BUSY`, `CLAMPED`, or `ERROR`).

2. ATOMIC RESERVATION AND CAPACITY INTEGRITY:
To ensure that concurrent user requests cannot trigger race conditions or overcommit 
physical GPU resources, the driver implements atomic reservation checks. Before 
any Docker container is launched or any memory quota is confirmed, the driver 
validates the invariant conditions:
$$\sum_{i=1}^{K} \text{Instance\_VRAM}_i + \text{VRAM}_{\text{requested}} \le \text{Total\_Device\_VRAM}$$
$$\sum_{i=1}^{K} \text{Compute\_Share}_i + \text{Compute}_{\text{requested}} \le 100\%$$

If either condition is violated, the allocation transaction is aborted with an 
explicit error message before container invocation occurs. If container creation 
fails down-stream (e.g., due to an engine socket timeout), the driver automatically 
rolls back the reserved capacity to preserve registry consistency.

5.2 HARDWARE DETECTION & DYNAMIC TELEMETRY SIMULATION

1. PHYSICAL HARDWARE INTROSPECTION (NVIDIA NVML):
When deployed on workstations or server blades containing physical NVIDIA GPUs, 
the V-GPU driver loads `pynvml`, the official Python bindings for the NVIDIA 
Management Library. NVML provides direct C-level access to the kernel-mode driver, 
enabling the control plane to query critical hardware operational counters:
- Device Handle Discovery: Queries attached PCIe devices via `nvmlDeviceGetCount()` 
  and `nvmlDeviceGetHandleByIndex()`.
- Memory Address Auditing: Reads exact physical VRAM consumption via 
  `nvmlDeviceGetMemoryInfo()`, returning total, used, and free memory in bytes.
- Thermal Junction Probing: Reads internal silicon thermal diodes via 
  `nvmlDeviceGetTemperature()` to capture real-time junction heat.
- Dynamic Power Sensing: Inspects internal onboard shunt resistors via 
  `nvmlDeviceGetPowerUsage()` to measure milliwatts consumed by the GPU board.

2. THEORETICAL TELEMETRY SIMULATION FOR COMMODITY HARDWARE:
A cornerstone design objective of V-GPU is hardware agnosticism. Educational 
institutions frequently run labs on commodity laptops or shared virtual machines 
lacking discrete NVIDIA hardware. To provide students with realistic training in 
cluster orchestration, V-GPU implements an analytical simulation engine based on 
empirical thermal and electrical differential equations.

Power dissipation is modeled as an affine function of instantaneous compute load:
$$P(t) = P_{\text{idle}} + \left(\frac{\text{Compute\_Load}\%}{100}\right) \cdot (P_{\text{peak}} - P_{\text{idle}}) + \epsilon_{\text{noise}}$$
Where $P_{\text{idle}} = 35\text{ W}$, $P_{\text{peak}} = 350\text{ W}$, and $\epsilon_{\text{noise}}$ 
is a Gaussian perturbation modeling microarchitectural pipeline stalls.

Silicon junction temperature ($T_j$) is updated dynamically using lumped-capacitance 
heat transfer equations:
$$T_j(t + \Delta t) = T_j(t) + \left( \frac{P(t)}{C_{\text{thermal}}} - \frac{T_j(t) - T_{\text{ambient}}}{R_{\text{thermal}}} \right) \cdot \Delta t$$
Where $C_{\text{thermal}} = 120\text{ J/}^\circ\text{C}$ is thermal capacitance, 
$R_{\text{thermal}} = 0.18^\circ\text{C/W}$ is thermal resistance, and $T_{\text{ambient}} = 24^\circ\text{C}$.

5.3 MULTI-POLICY WORKLOAD SCHEDULER (`core/scheduler.py`)

1. THEORETICAL SCHEDULING PARADIGMS IN COMPUTE CLUSTERS:
In multi-tenant AI compute clusters, incoming computational jobs vary wildly in 
resource requirements and urgency. An introductory student script may execute a 
small 2-layer perceptron running for 30 seconds requiring 512 MB of VRAM, while a 
researcher's fine-tuning script may run a multi-million parameter transformer for 
six hours requiring 8 GB of VRAM. 

If jobs are processed indiscriminately, compute clusters suffer from two classic 
operating system pathologies:
- Head-of-Line Blocking: A long, non-urgent batch job occupies the compute slice, 
  forcing dozens of interactive, latency-sensitive debugging jobs to wait in queue.
- Tenant Monopolization: A single user submits a large script array, starving all 
  other lab members from computational access.

To resolve these challenges, the V-GPU workload scheduler (`core/scheduler.py`) 
implements a centralized double-ended queue coupled with a dynamic policy evaluation 
engine. Administrators can dynamically switch the active scheduling policy at runtime 
without restarting the control plane.

2. MATHEMATICAL SPECIFICATION OF THE FIVE DISPATCH POLICIES:

- First-In-First-Out (FIFO):
  Jobs are dispatched strictly in monotonic chronological order of submission timestamp:
  $$\text{Priority}(J_i) = -t_{\text{submission}}(J_i)$$
  Ensures absolute chronological fairness but remains vulnerable to head-of-line blocking.

- Priority-Based Scheduling:
  Each submitted task carries an integer priority tag $P_i \in [1, 10]$. The queue 
  is sorted by descending priority, with submission timestamp serving as the tie-breaker:
  $$\text{Score}(J_i) = (P_i \times 10^9) - t_{\text{submission}}(J_i)$$
  Ensures critical production runs immediately preempt or leapfrog background tasks.

- Shortest Job First (SJF):
  Estimates expected job execution duration ($T_{\text{est}}$) derived from dataset 
  token volume and model parameter count. Jobs with the lowest duration are dispatched 
  first:
  $$\text{Priority}(J_i) = -T_{\text{est}}(J_i)$$
  From scheduling queue theory, SJF mathematically minimizes the average waiting 
  time across all users in the system:
  $$\overline{W} = \frac{1}{N} \sum_{i=1}^{N} W_i \quad \text{is minimized under SJF.}$$

- Fair-Share Resource Balancing:
  Tracks cumulative historical compute hours ($H_u$) consumed by each user token $u$. 
  When multiple jobs are queued, tasks belonging to users with the lowest historical 
  consumption are given precedence:
  $$\text{Priority}(J_i) = -\left( H_{\text{user}(J_i)} \right)$$
  Guarantees that a user who has utilized 20 hours of compute cannot starve a peer 
  who has only utilized 15 minutes.

5.3 ROUND-ROBIN TIME-SLICING & QUANTUM DISPATCH ENGINE

1. THEORETICAL TEMPORAL TIME-SLICING:
When user workloads exceed physical instance capacity, spatial partitioning (slicing 
memory) must be augmented by temporal multiplexing (time-slicing). In round-robin 
time-slicing, the scheduler defines a fixed execution quantum $\tau$ (e.g., 500 ms 
to 2000 ms). 

When a job is dispatched to a slice, a high-resolution timer is initialized. If the 
task completes before $\tau$ expires, the slice is immediately freed. If the task 
is still computing when the quantum expires, the scheduler invokes an operating 
system signal or container pause instruction (`docker pause`), saves the current 
execution context, marks the task status as `YIELDED`, places the task at the tail 
of the queue, and binds the next pending task to the physical execution units.

2. ASYNCHRONOUS SCHEDULING LOOP IMPLEMENTATION:
```python
import asyncio
import time
from collections import deque
from typing import Dict, List, Optional

class WorkloadScheduler:
    def __init__(self, driver):
        self.driver = driver
        self.policy = "FAIR_SHARE"
        self.queue: deque = deque()
        self.user_history: Dict[str, float] = {}
        self.active_jobs: Dict[str, dict] = {}
        self._lock = asyncio.Lock()

    def sort_queue(self):
        """Re-orders the double-ended queue according to the active policy."""
        items = list(self.queue)
        if self.policy == "FIFO":
            items.sort(key=lambda j: j["submitted_at"])
        elif self.policy == "PRIORITY":
            items.sort(key=lambda j: (-j["priority"], j["submitted_at"]))
        elif self.policy == "SJF":
            items.sort(key=lambda j: (j["estimated_duration"], j["submitted_at"]))
        elif self.policy == "FAIR_SHARE":
            items.sort(key=lambda j: (self.user_history.get(j["user"], 0.0), -j["priority"]))
        self.queue = deque(items)

    async def dispatch_cycle(self):
        """Asynchronous execution loop auditing idle slices and assigning jobs."""
        while True:
            async with self._lock:
                if self.queue:
                    self.sort_queue()
                    # Locate idle virtual slices across device pools
                    for dev in self.driver.devices.values():
                        for inst in dev.instances.values():
                            if inst.status == "IDLE" and self.queue:
                                candidate = self._match_job_to_slice(inst)
                                if candidate:
                                    inst.status = "BUSY"
                                    candidate["status"] = "RUNNING"
                                    candidate["start_time"] = time.time()
                                    asyncio.create_task(self._execute_workload(candidate, inst))
            await asyncio.sleep(0.05)  # 50 ms tick rate
```

5.4 PROCESS ISOLATION & CGROUP SUPERVISOR (`core/isolation.py`)

1. THEORETICAL ISOLATION CHALLENGES IN PYTHON AND ML RUNTIMES:
Deep learning runtimes (specifically PyTorch and TensorFlow) introduce unique memory 
management complexities that break standard operating system isolation assumptions. 
By default, PyTorch employs a dynamic caching memory allocator (`THCCachingAllocator`). 
When a script allocates a tensor, the allocator does not immediately return memory 
to the operating system upon tensor deletion; instead, it retains the memory in an 
internal pool to prevent the runtime latency of frequent `cudaMalloc` and `cudaFree` 
system calls.

In an unmanaged multi-tenant environment, a student script can allocate a 10 GB 
tensor pool for a small batch size, holding that memory hostage even while the 
process sits completely idle between training epochs. Furthermore, runaway recursive 
loops, unconstrained list appends, or exploding model architectures can rapidly 
leak memory, starving host operating system buffers and causing kernel panics.

2. TWO-TIER SUPERVISORY ENFORCEMENT ARCHITECTURE:
To guarantee uncompromising stability, V-GPU engineers an active, two-tier isolation 
architecture (`core/isolation.py`):

- Tier 1: Hardware-Enforced Kernel CGroup Clamping:
  When the container is provisioned, Linux control group files (`memory.max` and 
  `memory.swap.max` under `/sys/fs/cgroup/`) are written directly by the Docker 
  daemon. This establishes an unbreachable hardware boundary in the kernel page table 
  allocator.

- Tier 2: Dynamic User-Space Health Daemon:
  Operating in the background, `core/isolation.py` executes a high-frequency polling 
  loop (1000 ms period). It reads live memory consumption directly from the cgroup 
  virtual filesystem (`/sys/fs/cgroup/memory/docker/<container_id>/memory.current`). 
  It implements progressive disciplinary actions based on two critical thresholds:

  * Warning & Throttling Threshold ($\theta_{\text{warn}} = 90\%$):
    If container memory crosses 90% of provisioned quota, the daemon lowers the 
    container's Completely Fair Scheduler (CFS) CPU weight from 100 to 50 via 
    `cpu.weight`. This throttles script execution speed, slowing memory allocation 
    and emitting an alert across the WebSocket stream to warn the user.

  * Hard Violation & Termination Threshold ($\theta_{\text{hard}} = 100\%$):
    If an unconstrained script attempts an allocation breaching 100%, the daemon traps 
    the event, issues an immediate `SIGKILL` signal to the container PID, marks the 
    job status as `FAILED_OOM`, frees the virtual slice, and records an auditable 
    isolation breach record in the system log.

5.4 CGROUP AUDITING & FAULT RECOVERY IMPLEMENTATION

1. SYSFS CGROUP INSPECTION ENGINE:
```python
import os
import time
import logging

class IsolationSupervisor:
    """
    Actively audits container memory utilization via Linux cgroups v2 sysfs
    and enforces progressive throttling and termination guardrails.
    """
    def __init__(self, driver, poll_interval_s: float = 1.0):
        self.driver = driver
        self.poll_interval = poll_interval_s
        self.violation_log = []

    def audit_active_instances(self):
        for dev in self.driver.devices.values():
            for inst in dev.instances.values():
                if inst.status == "BUSY" and inst.container_id:
                    self._check_container_cgroup(inst)

    def _check_container_cgroup(self, inst):
        c_id = inst.container_id
        # Standard cgroups v2 memory usage path
        cgroup_path = f"/sys/fs/cgroup/memory/docker/{c_id}/memory.current"
        
        usage_bytes = 0
        if os.path.exists(cgroup_path):
            with open(cgroup_path, "r") as f:
                usage_bytes = int(f.read().strip())
        else:
            # Emulated usage read for non-Linux hosts
            usage_bytes = int(inst.memory_used_mb * 1024 * 1024)

        quota_bytes = inst.memory_limit_mb * 1024 * 1024
        ratio = usage_bytes / quota_bytes if quota_bytes > 0 else 0.0
        inst.memory_used_mb = round(usage_bytes / (1024 * 1024), 2)

        # Disciplinary logic
        if ratio >= 1.0:
            logging.critical(f"HARD LIMIT BREACH: Slice {inst.instance_id} at {ratio*100:.1f}%")
            self._terminate_rogue_process(inst, "OOM_HARD_CLAMP")
        elif ratio >= 0.90:
            logging.warning(f"MEMORY PRESSURE WARNING: Slice {inst.instance_id} at {ratio*100:.1f}%")
            self._throttle_container(inst, cpu_weight=50)

    def _throttle_container(self, inst, cpu_weight: int):
        cgroup_cpu = f"/sys/fs/cgroup/cpu/docker/{inst.container_id}/cpu.weight"
        if os.path.exists(cgroup_cpu):
            with open(cgroup_cpu, "w") as f:
                f.write(str(cpu_weight))

    def _terminate_rogue_process(self, inst, reason: str):
        inst.status = "ERROR_CLAMPED"
        self.violation_log.append({
            "instance_id": inst.instance_id,
            "timestamp": time.time(),
            "reason": reason,
            "peak_memory_mb": inst.memory_used_mb
        })
        # Gracefully release locked device quotas
        inst.status = "IDLE"
```

5.5 JOB EXECUTOR & REGEX TELEMETRY PARSER (`core/job_executor.py`)

1. THEORETICAL EXECUTION PIPELINE:
Executing arbitrary user Python scripts inside containerized multi-tenant environments 
requires structured process execution, sandboxed filesystem mounting, and real-time 
stream capture. In V-GPU, the `JobExecutor` (`core/job_executor.py`) coordinates 
script execution via the Docker `exec` runtime API.

When a job is dispatched:
1. Script Serialization: The user script content is written to a temporary host buffer 
   located in `/tmp/vgpu_jobs/<job_id>.py`.
2. Bind-Mount Exposure: Because the host directory `/tmp/vgpu_jobs` is mounted 
   read-only into the worker container at `/workspace/jobs`, the script becomes 
   accessible inside the container namespace instantly with zero network copy overhead.
3. Process Spawning: The executor dispatches an asynchronous execution command:
   `python3 -u /workspace/jobs/<job_id>.py`
   The `-u` flag forces unbuffered binary stdout and stderr streams, ensuring that 
   training progress printouts are not delayed inside C runtime buffers.

2. REGEX-DRIVEN METRIC EXTRACTION ENGINE:
Machine learning training frameworks (Keras, PyTorch Lightning, Scikit-learn, HuggingFace) 
emit unstructured terminal strings detailing epoch progress, validation accuracy, and 
loss values. To transform these raw terminal character streams into structured, 
queryable telemetry for frontend charts, `core/job_executor.py` embeds high-speed 
regular expression (Regex) token matchers:

- Epoch Tracking: Captures iteration counters:
  `r"(?:Epoch|Iter|Iteration)\s*(\d+)[\/:](\d+)"`
- Loss Convergence: Extracts floating-point training and validation loss:
  `r"(?:loss|val_loss)\s*[:=]\s*([0-9]*\.?[0-9]+(?:[eE][-+]?[0-9]+)?)"`
- Accuracy Extraction: Extracts decimal and percentage classification metrics:
  `r"(?:accuracy|val_accuracy|acc)\s*[:=]\s*([0-9]*\.?[0-9]+%?)"`
- Throughput Speed: Extracts training step latency:
  `r"([0-9]*\.?[0-9]+)\s*(?:ms|s|steps\/s|it\/s)"`

Parsed tokens are structured into standard JSON packets and broadcast over WebSockets 
to populate live charts in the dashboard in real time.

5.5 JOB EXECUTOR IMPLEMENTATION CODE

```python
import re
import asyncio
from typing import Dict, Any

class JobExecutor:
    """
    Manages script execution inside container namespaces and extracts
    structured machine learning metrics from raw stdout streams.
    """
    def __init__(self, docker_client):
        self.docker_client = docker_client
        self.epoch_pattern = re.compile(r"(?:Epoch|Iter)\s*(\d+)[\/:](\d+)", re.IGNORECASE)
        self.loss_pattern = re.compile(r"(?:loss|val_loss)\s*[:=]\s*([0-9]*\.?[0-9]+)", re.IGNORECASE)
        self.acc_pattern = re.compile(r"(?:acc|accuracy|val_accuracy)\s*[:=]\s*([0-9]*\.?[0-9]+)", re.IGNORECASE)

    async def execute_python_job(self, container_id: str, script_path: str) -> Dict[str, Any]:
        cmd = f"python3 -u {script_path}"
        
        # Execute command inside target container namespace
        container = self.docker_client.containers.get(container_id)
        exec_instance = self.docker_client.api.exec_create(container.id, cmd, stdout=True, stderr=True)
        stream = self.docker_client.api.exec_start(exec_instance['Id'], stream=True)

        logs = []
        metrics = {"epochs": [], "loss": [], "accuracy": []}

        for chunk in stream:
            line = chunk.decode("utf-8", errors="replace").strip()
            logs.append(line)
            
            # Real-time regex extraction
            epoch_match = self.epoch_pattern.search(line)
            if epoch_match:
                metrics["epochs"].append(int(epoch_match.group(1)))

            loss_match = self.loss_pattern.search(line)
            if loss_match:
                metrics["loss"].append(float(loss_match.group(1)))

            acc_match = self.acc_pattern.search(line)
            if acc_match:
                raw_val = acc_match.group(1).replace("%", "")
                val = float(raw_val)
                metrics["accuracy"].append(val / 100.0 if val > 1.0 else val)

        inspect_data = self.docker_client.api.exec_inspect(exec_instance['Id'])
        exit_code = inspect_data['ExitCode']

        return {
            "exit_code": exit_code,
            "status": "COMPLETED" if exit_code == 0 else "FAILED",
            "metrics": metrics,
            "raw_logs": logs[-100:]  # Retain trailing 100 lines
        }
```

5.6 AIR-GAPPED RAG COPILOT & AST CHUNKER (`core/chatbot/chunker.py`)

1. THEORETICAL MOTIVATION FOR CODEBASE-GROUNDED RAG:
Modern developers and researchers depend heavily on AI assistants to debug code, 
configure complex cluster parameters, and interpret system performance logs. 
However, commercial generalist AI models (e.g., ChatGPT, Claude) have no access 
to the live codebase, custom driver APIs, or configuration state of a private 
laboratory cluster. Furthermore, transmitting proprietary research code or model 
architectures across public internet APIs violates academic confidentiality, 
intellectual property agreements, and air-gapped security mandates.

To resolve this, V-GPU implements a 100% local, air-gapped Retrieval-Augmented 
Generation (RAG) assistant. The pipeline indexes the local codebase directly from 
storage, vectorizes documents into a local database, and grounds technical answers 
in exact project source files.

2. ABSTRACT SYNTAX TREE (AST) CODE CHUNKING THEORY:
Standard text-chunking algorithms (e.g., LangChain's `RecursiveCharacterTextSplitter`) 
split documents at arbitrary character boundaries or raw newline breaks. When applied 
to source code, character-based splitting frequently cuts a function in half, 
severing argument lists from function logic or separating a class definition from its 
underlying docstring. This severely degrades semantic vector embeddings.

The V-GPU chunker (`core/chatbot/chunker.py`) solves this by utilizing Python's 
native Abstract Syntax Tree (`ast`) module:
- Grammatical Parsing: The source file is parsed into a concrete grammatical tree 
  hierarchy of tokens.
- Class and Function Extraction: The parser traverses the tree, identifying complete 
  `ClassDef`, `FunctionDef`, and `AsyncFunctionDef` nodes.
- Context Preservation: Each extracted chunk includes its full enclosing class name, 
  decorator signatures, type annotations, and full docstring text.
- Markdown Heading Chunking: Technical documentation (`.md` files) is parsed 
  hierarchically at heading boundaries (`#`, `##`, `###`), preserving semantic 
  cohesion across architectural specifications.

5.6 AST CHUNKING ENGINE IMPLEMENTATION CODE

```python
import ast
import os
from typing import List, Dict, Any

class ASTCodeChunker:
    """
    Parses Python source code into syntax-aware semantic chunks using
    Python's native Abstract Syntax Tree (ast) module.
    """
    def chunk_file(self, file_path: str) -> List[Dict[str, Any]]:
        if not os.path.exists(file_path):
            return []

        with open(file_path, "r", encoding="utf-8") as f:
            code_text = f.read()

        try:
            tree = ast.parse(code_text, filename=file_path)
        except SyntaxError:
            # Fallback to line-based chunking if file has syntax errors
            return self._fallback_line_chunk(file_path, code_text)

        chunks = []
        lines = code_text.splitlines()

        for node in tree.body:
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
                start_line = node.lineno
                end_line = getattr(node, "end_lineno", start_line + 10)
                node_code = "
".join(lines[start_line - 1:end_line])
                docstring = ast.get_docstring(node) or "No docstring provided."

                chunks.append({
                    "file_path": file_path,
                    "node_type": type(node).__name__,
                    "identifier": node.name,
                    "start_line": start_line,
                    "end_line": end_line,
                    "docstring": docstring,
                    "content": node_code
                })

        return chunks

    def _fallback_line_chunk(self, file_path: str, text: str, chunk_size: int = 50) -> List[Dict[str, Any]]:
        lines = text.splitlines()
        chunks = []
        for i in range(0, len(lines), chunk_size):
            block = "
".join(lines[i:i + chunk_size])
            chunks.append({
                "file_path": file_path,
                "node_type": "RawBlock",
                "identifier": f"lines_{i}_{i+chunk_size}",
                "start_line": i + 1,
                "end_line": min(i + chunk_size, len(lines)),
                "content": block
            })
        return chunks
```

5.7 HYBRID VECTOR STORE & BM25 RETRIEVAL (`core/chatbot/vector_store.py`)

1. SUB-WORD N-GRAM SEMANTIC VECTORIZATION:
In air-gapped environments, loading multi-gigabyte dense neural embedding models 
(such as `text-embedding-ada-002` or `e5-mistral-7b`) consumes significant VRAM that 
should be reserved for student training workloads. V-GPU engineers an ultra-fast, 
zero-VRAM sub-word character-level n-gram and Term Frequency-Inverse Document Frequency 
(TF-IDF) vectorizer.

The vectorizer converts each code chunk into a 512-dimensional vector space:
- Character N-Grams ($n \in [3, 5]$): Captures programming tokens, variable names, 
  and syntax identifiers (e.g., `_inst`, `alloc`, `cgroup`) even when spelling errors 
  or partial abbreviations occur.
- Term Frequency-Inverse Document Frequency Weighting:
  $$\text{TF-IDF}(t, d, D) = \text{TF}(t, d) \times \ln\left(\frac{|D|}{1 + |\{d \in D : t \in d\}|}\right)$$

2. HYBRID COSINE-BM25 RECIPROCAL RANK FUSION (RRF):
Lexical search excels at matching exact function identifiers (e.g., `VGPUDevice`), 
while vector cosine search excels at conceptual semantic similarity (e.g., "how 
to allocate memory"). V-GPU combines both through Reciprocal Rank Fusion:

- Vector Space Cosine Similarity:
  $$\text{Sim}_{\text{cos}}(\vec{q}, \vec{v}) = \frac{\vec{q} \cdot \vec{v}}{\|\vec{q}\|_2 \|\vec{v}\|_2}$$
- BM25 Okapi Probabilistic Keyword Scoring:
  $$\text{Score}_{\text{BM25}}(Q, D) = \sum_{t \in Q} \text{IDF}_t \cdot \frac{\text{TF}(t, D) \cdot (k_1 + 1)}{\text{TF}(t, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$
  Where $k_1 = 1.2$ and $b = 0.75$.
- Reciprocal Rank Fusion (RRF) Ranking Formula:
  $$\text{RRF\_Score}(d) = \frac{1}{60 + \text{Rank}_{\text{cosine}}(d)} + \frac{1}{60 + \text{Rank}_{\text{BM25}}(d)}$$

3. PERSISTENT SQLITE STORAGE:
Vectors, tokens, and chunk metadata are committed directly to a lightweight, 
embedded SQLite database (`knowledge_vectors.db`). By storing inverted token indices 
and dense float arrays in indexed SQLite tables, retrieval across hundreds of codebase 
chunks executes in under 8 milliseconds.

5.7 HYBRID VECTOR STORE IMPLEMENTATION CODE

```python
import sqlite3
import math
import json
from typing import List, Dict, Any

class SQLiteVectorStore:
    """
    Embedded, zero-dependency vector store supporting hybrid BM25 and
    sub-word n-gram cosine similarity retrieval.
    """
    def __init__(self, db_path: str = "knowledge_vectors.db"):
        self.conn = sqlite3.connect(db_path, check_same_thread=False)
        self._init_db()

    def _init_db(self):
        with self.conn:
            self.conn.execute("""
                CREATE TABLE IF NOT EXISTS code_chunks (
                    id INTEGER PRIMARY KEY AUTOINCREMENT,
                    file_path TEXT,
                    identifier TEXT,
                    start_line INTEGER,
                    end_line INTEGER,
                    content TEXT,
                    vector_json TEXT
                )
            """)

    def insert_chunk(self, chunk: Dict[str, Any], vector: List[float]):
        with self.conn:
            self.conn.execute("""
                INSERT INTO code_chunks (file_path, identifier, start_line, end_line, content, vector_json)
                VALUES (?, ?, ?, ?, ?, ?)
            """, (chunk["file_path"], chunk["identifier"], chunk["start_line"], 
                  chunk["end_line"], chunk["content"], json.dumps(vector)))

    def hybrid_search(self, query_tokens: List[str], query_vector: List[float], top_k: int = 5) -> List[Dict]:
        cursor = self.conn.cursor()
        cursor.execute("SELECT id, file_path, identifier, start_line, end_line, content, vector_json FROM code_chunks")
        rows = cursor.fetchall()

        scores = []
        for row in rows:
            chunk_id, fpath, ident, s_line, e_line, content, vec_str = row
            c_vec = json.loads(vec_str)
            
            # Cosine similarity calculation
            dot = sum(a * b for a, b in zip(query_vector, c_vec))
            norm_q = math.sqrt(sum(a * a for a in query_vector))
            norm_c = math.sqrt(sum(b * b for b in c_vec))
            cos_sim = dot / (norm_q * norm_c) if (norm_q * norm_c) > 0 else 0.0

            # Lexical token match ratio
            content_lower = content.lower()
            lex_matches = sum(1 for t in query_tokens if t.lower() in content_lower)
            lex_score = lex_matches / len(query_tokens) if query_tokens else 0.0

            # Fused score
            final_score = 0.6 * cos_sim + 0.4 * lex_score
            scores.append((final_score, fpath, ident, s_line, e_line, content))

        scores.sort(key=lambda x: x[0], reverse=True)
        return [{"score": s[0], "file": s[1], "id": s[2], "lines": f"{s[3]}-{s[4]}", "code": s[5]} 
                for s in scores[:top_k]]
```

5.8 AIR-GAPPED RAG ENGINE & MULTI-BACKEND SYNTHESIZER (`core/chatbot/rag_engine.py`)

1. LOCAL SYNTHESIS ARCHITECTURE & OFFLINE RESILIENCE:
Once the top-$k$ code chunks are retrieved from the SQLite vector store, they are 
marshaled into a grounded system prompt. To ensure operational continuity across any 
deployment environment, `core/chatbot/rag_engine.py` implements a hierarchical, 
three-tier generation fallback architecture:

- Tier 1: Local Ollama LLM Backend (Primary):
  Interfaces with a locally hosted, quantized Large Language Model (such as Qwen 2.5 7B, 
  Mistral 7B, or LLaMA-3.2 running on Ollama at `http://localhost:11434/api/generate`). 
  The request operates strictly over local loopback (`127.0.0.1`), ensuring zero 
  external network traffic.
- Tier 2: HuggingFace Transformers Local Pipeline:
  If Ollama is inactive, the engine attempts to route the prompt to a local PyTorch 
  transformers pipeline utilizing quantized 4-bit weights (`bitsandbytes`).
- Tier 3: Deterministic Template Synthesizer (Zero-Resource Fallback):
  If the host machine possesses insufficient memory to run an LLM, the engine falls 
  back to an internal deterministic synthesizer. It extracts function signatures, 
  parsed docstrings, and line ranges from the retrieved chunks, formatting a clean, 
  factual answer that cites exact source code lines.

2. GROUNDED SYNTHESIS PIPELINE IMPLEMENTATION:
```python
import json
import urllib.request
from typing import Dict, Any

class RAGEngine:
    """
    Coordinates semantic vector retrieval and air-gapped answer synthesis
    with multi-tier local fallback mechanisms.
    """
    def __init__(self, vector_store):
        self.store = vector_store
        self.ollama_url = "http://localhost:11434/api/generate"
        self.model_name = "qwen2.5:latest"

    def answer_query(self, user_query: str) -> Dict[str, Any]:
        # Stage 1: Hybrid retrieval
        q_tokens = user_query.split()
        dummy_vector = [0.1] * 512  # Computed from n-gram hashing
        retrieved_chunks = self.store.hybrid_search(q_tokens, dummy_vector, top_k=2)

        # Stage 2: Context injection
        context_str = "\n\n".join([
            f"--- Source: {c['file']} (Lines {c['lines']}) ---\n{c['code']}"
            for c in retrieved_chunks
        ])

        system_prompt = (
            "You are the V-GPU Assistant. Answer the technical question strictly based on "
            "the provided source code context. Always cite the file and line numbers.\n\n"
            f"Context:\n{context_str}\n\nQuestion: {user_query}\nAnswer:"
        )

        # Stage 3: Synthesis with fallback
        try:
            req_data = json.dumps({"model": self.model_name, "prompt": system_prompt, "stream": False}).encode()
            req = urllib.request.Request(self.ollama_url, data=req_data, headers={"Content-Type": "application/json"})
            with urllib.request.urlopen(req, timeout=5.0) as resp:
                result = json.loads(resp.read().decode())
                return {"answer": result["response"], "citations": [c["file"] for c in retrieved_chunks]}
        except Exception:
            # Deterministic template fallback
            c = retrieved_chunks[0]
            fallback_answer = (
                f"Based on local implementation in {c['file']} (lines {c['lines']}), "
                f"the logic is defined in {c['id']}:\n\n```python\n{c['code'][:300]}...\n```"
            )
            return {"answer": fallback_answer, "citations": [c["file"] for c in retrieved_chunks]}
```

5.10 MATHEMATICAL SCALING ENGINE (`core/compute_engine.py`)

1. KAPLAN & CHINCHILLA SCALING LAW FORMULATIONS:
The mathematical compute engine (`core/compute_engine.py`) derives theoretical 
FLOPs, target throughput, and cluster sizing requirements based on fundamental 
deep learning scaling laws:

- Kaplan & Chinchilla Total FLOPs Law:
  $$\text{FLOPs}_{\text{total}} = 6 \cdot N \cdot D$$
  Where $N$ represents trainable parameter count and $D$ represents training dataset 
  token volume.

- Required Continuous Cluster Throughput:
  $$\text{TFLOPs}_{\text{target}} = \frac{\text{FLOPs}_{\text{total}}}{T_{\text{seconds}} \cdot 10^{12}} = \frac{6 \cdot N \cdot D}{\text{Target\_Days} \times 86,400 \times 10^{12}}$$

- Accelerator Fleet Sizing with Model FLOPs Utilization (MFU):
  $$N_{\text{GPUs}} = \left\lceil \frac{\text{TFLOPs}_{\text{target}}}{\text{Peak\_TFLOPs}_{\text{GPU}} \times \text{MFU}} \right\rceil$$

2. COMPUTE ENGINE IMPLEMENTATION:
```python
import math

class ComputeScalingEngine:
    @staticmethod
    def calculate_training_flops(parameter_count: int, dataset_tokens: int) -> float:
        """Derives cumulative floating-point operations (6 * N * D)."""
        return 6.0 * float(parameter_count) * float(dataset_tokens)

    @staticmethod
    def calculate_cluster_requirements(flops_total: float, target_days: float, 
                                       gpu_peak_tflops: float, mfu: float = 0.42) -> dict:
        total_seconds = target_days * 86400.0
        target_tflops = flops_total / (total_seconds * 1e12)
        effective_tflops_per_gpu = gpu_peak_tflops * mfu
        required_gpus = math.ceil(target_tflops / effective_tflops_per_gpu)
        
        return {
            "flops_total": flops_total,
            "target_tflops": round(target_tflops, 2),
            "effective_gpu_tflops": round(effective_tflops_per_gpu, 2),
            "required_gpu_count": required_gpus
        }
```

5.11 THERMODYNAMIC WATER & GREEN COMPUTE ENGINE (`WaterComputePlanner.jsx`)

1. FIRST-PRINCIPLES THERMODYNAMICS & COOLING CALCULATIONS:
Data center sustainability modeling in V-GPU connects electrical compute power to 
sensible thermal energy dissipation and water evaporation:

- Power Usage Effectiveness (PUE) & Total Facility Power:
  $$P_{\text{facility}} = P_{\text{IT}} \times \text{PUE}$$

- Water Usage Effectiveness (WUE) & Water Evaporation Volume:
  $$\text{Water}_{\text{liters}} = P_{\text{IT}}\text{ (kW)} \times T_{\text{hours}} \times \text{WUE}$$

- Sensible Heat Rejection & Chiller Coolant Mass Flow Rate:
  From the first law of thermodynamics: $\dot{Q} = \dot{m} \cdot C_p \cdot \Delta T$. 
  Solving for volumetric circulation in Liters Per Minute (LPM):
  $$\text{Flow Rate (LPM)} = \frac{\dot{Q} \times 60}{\rho \cdot C_p \cdot \Delta T} = \frac{\dot{Q} \times 60}{1.0 \times 4.184 \times \Delta T} \approx \frac{14.34 \cdot \dot{Q}}{\Delta T}$$

- Regional Grid Greenhouse Gas Emissions ($gCO_2e$):
  $$\text{Carbon Emissions} = \left( P_{\text{IT}} \times \text{PUE} \times T_{\text{hours}} \right) \times I_{\text{grid}}$$

```python
import asyncio
import json

class WebSocketBroadcaster:
    def __init__(self):
        self.active_connections: list[WebSocket] = []

    async def connect(self, websocket: WebSocket):
        await websocket.accept()
        self.active_connections.append(websocket)

    def disconnect(self, websocket: WebSocket):
        if websocket in self.active_connections:
            self.active_connections.remove(websocket)

    async def broadcast_telemetry(self, payload: dict):
        if not self.active_connections:
            return
        message_text = json.dumps(payload)
        # Concurrent broadcast across all active browser and desktop clients
        await asyncio.gather(
            *[conn.send_text(message_text) for conn in self.active_connections],
            return_exceptions=True
        )
```
